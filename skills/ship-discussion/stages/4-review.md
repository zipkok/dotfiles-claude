# Ship-Discussion · Review 단계 (참조 문서)

`SKILL.md`가 3~5단계에서 `workflows/ship-discussion-panel.js`(`stage: 'pipeline'`)를 호출할 때 그
안에서 수행되는 Review 부분의 상세 정의. **result(실행) 이전에 계획을 검증하는 게이트**다 —
ship-develop의 review-plan과 같은 위치. 정성(steel-man)과 정량(스코어링 루브릭)을 함께 반영하는
**하이브리드 게이트**다. fail시 Plan 재작업 루프(최대 2회)와 3회째 에스컬레이션은 워크플로 내부에서
자동으로 처리된다 — Main이 매번 재호출하지 않는다. (디버깅 목적으로 `stage: 'review'`만 개별 호출도
가능)

- **역할**: plan이 실제 논쟁(Result)으로 넘어가도 될 만큼 탄탄한지 검증
- **실행**: `steel-man`을 적용하는 `agents/ship-discussion-technique-agent.md` 1회 + `agents/
  ship-discussion-synthesizer.md`가 steel-man 결과와 plan의 대안·평가기준을 받아 정성 판정과 정량
  채점을 함께 수행

## 왜 steel-man만 남았나 (pre-mortem·decision-review·rubber-duck을 뺀 이유)

처음엔 spex 스타일로 pre-mortem·decision-review까지 3개를 썼으나, "위임한 걸 매번 재구성·재검증하면
분업의 의미가 사라진다"는 피드백을 계기로 재검토했다:
- **pre-mortem 제외**: Plan 단계가 이미 같은 질문("이 진행대로 하면 뭐가 문제될지")을 물었다 —
  Review가 똑같이 또 물으면 Plan에 위임한 검증을 처음부터 재검증하는 것과 같다
- **decision-review 제외**: 이 기법은 "시간이 지나 결과를 안 뒤 그때 결정이 합리적이었나"를 보는
  건데, 계획을 막 세운 직후(시간도 안 지나고 결과도 없음)에 적용하는 건 전제 자체가 안 맞는다
- **rubber-duck 제외 (1:1 대체 아님)**: rubber-duck은 "계획을 처음부터 끝까지 설명했을 때 말이
  되는가"(정합성)를 봤다. 아래 정량 루브릭은 그 역할을 이어받는 게 아니라, Review의 목적 자체를
  "계획이 말이 되는가" 검증에서 "이 결정을 지지할 근거가 충분한가" 채점으로 바꾼 것이다 — 다루는
  질문이 다르다
- **steel-man만 유지**: Plan의 4개 기법이 안 본 각도다 — "입장 A/B가 실제로 대립하는가, 최강
  버전으로 설정됐는가"(Plan은 Result의 position 분화를 모른 채 진행됨)

## 할 일 (워크플로 안에서 에이전트들이 수행)

1. steel-man이 plan.md(대안·평가기준 포함)를 검증 — 입장 A/B가 진짜 대립하는지, 최강 버전으로
   설정됐는지
2. synthesizer가 아래를 수행:
   - steel-man 지적을 CRITICAL/경미로 분류
   - plan의 "대안 × 평가기준"으로 스코어링 매트릭스를 채점해 쟁점별 순위 산출
   - 5개 하위항목(1·2위 격차/근거 기반 비율/소수의견 기록/권고안 지지율/판정 기준 충족 전망)을
     0/1/2로 채점 → 게이트 점수 = (합÷10)×100
   - aporia/미해결 쟁점은 채점 분모에서 제외하되 "채점 제외 — 사유"로 명시
   - 정성 + 정량을 합쳐 하이브리드 판정

## 하이브리드 판정 밴드

| 조건 | 판정 | 처리 |
|------|------|------|
| CRITICAL 없음 **and** 점수≥80 | 통과 | 5단계(Result)로 진행 |
| CRITICAL 없음 **and** 60≤점수<80 | 조건부 통과 | 이월표에 미달 항목 등록 후 Result 진행, Result
  완료 전 해소 |
| CRITICAL 있음 **or** 점수<60 | fail | 3단계(Plan)로 루프백, 보강 지점 구체 명시 |

## 루프 상한 + 에스컬레이션

Review→Plan 재작업이 **같은 게이트에서 2회를 초과**(즉 3회째 다시 fail)하면, `AskUserQuestion`으로
사용자에게 **수용(현재 계획으로 강행) / 보류(다른 세션에서 재검토) / 폐기(이 쟁점 포기)** 중 하나를
직접 결정하도록 요청한다 — Spec의 "2회 재작성 후 사용자 개입"과 같은 모양이다. Main이 재작업 여부를
스스로 무한정 판단하지 않는다.

## 게이트 우회 금지

- 미달 상태를 "대략 괜찮음"으로 넘기지 않는다
- 채점 근거 없이 점수만 적지 않는다 (5개 하위항목 각각 근거 필요)
- 단계 생략 제안(예: "Review 없이 바로 Result로") 을 거부한다

```md

## 기법별 발견
- steel-man: {입장 A/B가 진짜 대립하는지, 최강 버전으로 설정됐는지}

## 채점
| 하위항목 | 점수(0/1/2) | 근거 |
|----------|-------------|------|
| 1·2위 가중총점 격차 | | |
| 근거 기반 비율 | | |
| 소수의견 기록·검토 | | |
| 권고안 지지율 | | |
| 판정 기준 충족 전망 | | |
| **합계 / 10** | | |

**게이트 점수 = (합÷10)×100 = ___ 점**

## 채점 제외 (aporia/미해결)
{쟁점명 — 사유. 없으면 "해당 없음"}

## 판정
- 결과: 통과 | 조건부 통과 | fail
- 근거: {정성+정량이 어떻게 반영됐는지}
- (조건부 통과) 이월 항목: 다음 표
- (fail) 보강 지점: {구체적으로}

## 이월(carry-over) 표 (조건부 통과 시만)
| 항목 | 미달 수치 | 영향 | 담당 | 해소 마감 | 상태 |
|------|-----------|------|------|-----------|------|
| | | | | Result 전 | 진행 |
```

## 게이트 조건

- `fail`이면 3단계(Plan)로 돌아가 지적된 지점을 보강한다 — result로 넘어가지 않는다
- `조건부 통과`면 이월표가 반드시 있어야 하고, Result 완료 전 해소 여부를 확인한다
- `통과`여도 근거 없이 통과시키지 않는다 — steel-man 지적과 5개 채점 항목 모두 판정에 반영됐는지
  확인
- aporia/미해결 쟁점이 있으면 채점에서 명시적으로 제외됐는지 확인 (조용히 빠진 게 아닌지)
