# Ship-Discussion · Clarify 단계 (참조 문서)

`SKILL.md`가 2단계에서 인라인으로 수행하는 절차의 상세 정의.

**역할**: spec에서 나온 쟁점들의 애매한 정의·범위·전제를 확정한다
**기법**: `socratic-method` (유형1 쟁점에만 적용)

## 유형 판정 — 왜 나눴는가

실사용(`docs/rfc/0002-improve-work-quality/`) 결과 모든 쟁점을 예외 없이 사용자와의 실시간
소크라테스식 대화로 처리했더니 왕복이 과도하게 늘었다. 그런데 쟁점의 모호함은 사실 두 종류다:

- **유형1 (사용자 고유 의도)**: "사용자가 이 표현으로 정확히 무슨 뜻을 의도했는가" — 이건 사용자
  본인만 답할 수 있다. 에이전트가 대신 추측하면 clarify의 존재 이유(사용자 의도 확인) 자체가
  무너진다.
- **유형2 (내적 일관성)**: "이 쟁점이 다른 쟁점·전제와 모순되지 않는가" — 이건 이미 확보된 정보
  (spec의 다른 쟁점, 지금까지 나온 답변)만으로 Main이 논리적으로 판단할 수 있다.

**판단 기준**: 쟁점 문구가 사용자만 아는 배경지식·의도·선호를 요구하면 유형1. 이미 있는 정보만으로
검증 가능하면 유형2. 애매하면 유형1로 취급한다 — 잘못 넘겨짚는 것보다 한 번 더 묻는 게 안전하다.

## 왜 socratic-method가 여기인가 (유형1)

이 기법은 위키에서 "이미 나온 하나의 주장을 질문으로 깊이 파고드는" 절차로 정의돼 있다. Spec은 아직
쟁점 자체가 없는 발산 단계라 안 맞고, Result는 이제 에이전트끼리 논쟁하는 구조라 사용자와의 대화가
아니게 됐다. Clarify(유형1)는 spec에서 이미 나온 쟁점(=주장)을 놓고 그 정의를 깊이 파고드는 단계라
이 기법의 원래 절차와 정확히 맞는다.

## 쟁점 선정 (Spec의 Self-Review 결과 활용)

모든 쟁점을 순서 없이 훑지 않는다 — Spec 단계 Self-Review 게이트의 **red-flag 탐지 목록** +
`[NEEDS CLARIFICATION]` 마킹 목록을 우선순위로 삼는다. 그 목록에 있는 쟁점부터 유형 판정과 아래
절차를 적용하고, 목록에 없는 쟁점은 시간이 남으면 다룬다 (전부 다룰 필요는 없다 — 둘 다 없었다는
것 자체가 명료했다는 신호).

## 모호어 탐지 (Spec의 red-flag 스캔을 이어받아 씀)

Spec이 이미 기계적으로 스캔한 red-flag 단어 목록(`should`, `might/could`, `fast/slow` 등)에 더해,
Clarify 진입 시점에 "개선", "빠르게", "충분히", "적절히" 같이 **측정도 합의도 안 되는 한국어 표현**을
쟁점 문구에서 한 번 더 훑는다. 새 스캔을 처음부터 다시 하는 게 아니라, Spec의 목록을 이어받아
Clarify의 언어(한국어)에 맞는 항목을 보태는 것 — 이렇게 찾은 표현이 있는 쟁점은 유형1 우선순위에
자동으로 들어간다 (모호어는 대개 "사용자가 정확히 뭘 의도했는지"의 문제이기 때문).

## 유형2 절차 (Main 자체 판단, 사용자 대화 없음)

1. 쟁점의 함의를 Main이 스스로 추적한다 (유형1의 "함의 도출"과 같은 작업, 사용자 답변 대신 spec/
   clarify에 이미 있는 정보로 수행)
2. 다른 쟁점·전제와 충돌하는 지점이 있는지 검토한다 (유형1의 "반례 제시"에 해당)
3. 결론을 셋 중 하나로 낸다: **일관됨** / **재정의 필요**(Main이 재정의 초안 작성) / **모순 발견**
4. 결론이 "재정의 필요" 또는 "모순 발견"이면서 **그 원인이 쟁점 자체가 아니라 spec의 전제**에 있다고
   판단되면, 배치 확인으로 넘기지 않고 즉시 사용자와의 라이브 대화로 에스컬레이션한다 (1단계 Spec으로
   돌아가는 흐름과 동일하게 취급 — 개별 쟁점 재정의가 아니라 spec 자체를 다시 짜야 하는 문제이기
   때문)
5. 그 외의 경우, 결론을 유형1 쟁점을 순차로 다루는 흐름 중 적절한 지점에 "이렇게 정리했습니다,
   맞나요?" 형태의 확인 질문 하나로 끼워 넣어 사용자 승인만 받는다 (새 대화를 열지 않되, 여러 개를
   억지로 한 호출에 묶지도 않는다)

## 유형1 절차 (쟁점마다 반복, 사용자와 대화 — 하나씩 순차로)

**왜 배치하지 않는가**: Spec 단계는 여러 질문을 한 `AskUserQuestion` 호출에 배치하지만(1단계 참조),
Clarify의 socratic-method는 그렇게 하지 않는다 — 다음 질문(함의 도출·반례 제시)이 **직전 답변에
따라 달라지는 적응적 구조**라, 배치해서 한꺼번에 물으면 뒤 질문들이 아직 안 나온 답을 전제로 하게
돼 대화가 성립하지 않는다. Spec의 발산 로테이션(mind-mapping 등)은 각 질문이 서로 독립적이라
배치가 통했지만, 여기선 통하지 않는다.

1. **주장 제시**: spec의 쟁점 문구 자체를 "주장"으로 삼는다
2. **명료화 질문**: `AskUserQuestion` 도구로 "이게 정확히 무슨 뜻인가요?"류 정의를 요구한다 — 질문자가
   답을 넣지 않는다. **한 번에 하나씩만** 묻는다
3. **함의 도출**: 사용자가 내놓은 정의에서 논리적으로 따라 나오는 결과를 함께 추적한다
4. **반례 제시**: 그 함의가 이미 확인된 다른 쟁점·전제와 충돌하는 지점이 있으면 질문으로 드러낸다
   (질문자가 "이건 모순이다"라고 단정하지 않는다 — 질문으로 사용자가 스스로 보게 한다)
5. **재정의 또는 aporia**:
   - 사용자가 스스로 정의를 수정하면 → 그 재정의를 기록
   - 답이 안 나오고 "사실 이건 불확실했다"는 상태(aporia)에 도달하면 → 그 자체를 유효한 결과로
     기록 (실패가 아니다)

## 함정 (위키 socratic-method.md에서)

- **유도신문 금지**: 질문자가 답을 미리 정해두고 그쪽으로 몰아가면 문답이 아니라 설득이 된다
- **시간 박스**: "왜?"를 무한히 캐면 사용자가 지치거나 방어적으로 변한다 — 쟁점당 3~4회 왕복을
  넘기면 다음 쟁점으로 넘어간다 (aporia로 남겨도 됨)
- **aporia는 실패가 아니다**: 명확한 답 없이 끝나는 것도 정당한 결과다

## Coverage 게이트 (socratic-method 대화 종료 후)

**주의**: 이 게이트는 "어떻게 대화할지"(socratic-method)와 다른 층위다 — 대화가 **무엇을 다뤘는지**
사후에 점검하는 것이라 절차 자체는 안 바꾸고 끝에서만 확인한다.

spec-kit `/speckit-clarify`의 10개 카테고리 중 소프트웨어 전용(Domain & Data Model, UX Flow,
Non-Functional Quality, Integration & External Dependencies)을 뺀 **5개 범용 범주**를 Clear/Partial/
Missing으로 스캔한다:

| 범주 | 확인할 것 |
|------|----------|
| 스코프/경계 | 이 논의에서 다루는 것과 명시적으로 제외하는 것이 구분됐는가 |
| 예외/한계 상황 | "이런 경우엔 어떻게 되는가" 같은 예외 케이스가 논의됐는가 |
| 제약·트레이드오프 | 어떤 제약(시간·자원·되돌리기 어려움 등) 안에서 판단하는지 나왔는가 |
| 용어 정의 | 핵심 용어의 의미가 사용자 자신의 말로 정의됐는가 |
| 완료 신호 | "이게 해결됐다"를 무엇으로 판단할지 나왔는가 |

**실패시 처리**: Missing으로 남은 범주가 있으면, 그 범주만 골라 socratic-method 절차(명료화 질문 →
함의 도출 → 재정의/aporia)를 한 라운드 더 진행한다. 전부 Clear 또는 Partial(aporia로 남기기로 한
경우 포함)이면 통과.

## 출력

```md
## 쟁점별 명확화
### {쟁점명} — 유형: {유형1 | 유형2}

(유형1)
- 명료화 질문: {질문}
- 사용자 정의: {답변}
- 함의: {추적한 논리적 결과}
- 결과: 재정의={새 정의} | aporia={불확실함이 드러난 지점}

(유형2)
- Main 판단: {추적한 함의 + 충돌 검토}
- 결론: 일관됨 | 재정의 필요(초안: {...}) | 모순 발견({충돌 지점})
- 사용자 승인: {승인 | 에스컬레이션(사유: spec 전제 문제)}

## Coverage 게이트 결과
| 범주 | 상태 |
|------|------|
| 스코프/경계 | Clear \| Partial \| Missing |
| 예외/한계 상황 | |
| 제약·트레이드오프 | |
| 용어 정의 | |
| 완료 신호 | |
```

## 게이트 조건

- 모든 쟁점이 유형2로만 분류되면 안 된다 — 최소 1개는 유형1로 분류돼 위 유형1 절차를 실제로 끝까지
  거쳐야 한다 (사용자 대화가 아예 없는 Clarify는 무효)
- aporia로 끝난 쟁점이 있어도 게이트 통과에는 지장 없다 (aporia 자체를 기록했다면 충분)
- Coverage 게이트의 5개 범주 중 Missing이 하나라도 남으면 3단계(Plan)로 진행할 수 없다
